1. Current System Summary

An offline Flutter 3.47.5 game (≈22.4k Dart LOC) for Android. It uses Riverpod state, Flame scenes and bundled JSON lessons. All data lives in one Hive key containing a JSON blob: {schemaVersion:3, activeChildId, children:{id → {profile, settings, dailySeconds, subjects.science{attempts, journeys}}}}. There are no accounts, no network and no permissions. Multiple child profiles share a device behind a parent gate.

What the user wants to move to a server (the "data" in this product): parent account, child profiles, per-child settings, assessment attempts (scores), in-progress lesson state ("journeys"), and usage time. Lesson content stays bundled in the apps and is versioned by contentVersion.

Target user journey. A parent creates an account by email on Android, logs in and links the local children. Play results are saved locally and synced. Later the parent opens the web app on a computer, logs in with the same email, sees the same children and progress, and edits a child's settings. Android pulls the change on its next sync (on resume, within 15 minutes, or via "Sync now").

6. Database Architecture

Every primary key of a synced entity is a client-generated UUIDv7. Clients create records offline without collisions, IDs sort by time (index-friendly), and Postgres stores them natively. UUIDv7 was chosen over ULID for the native uuid type. Auto-increment IDs are not used for synced entities.

Sync cursor. A global sequence change_seq_seq. Every insert, update or tombstone sets change_seq = nextval() inside the same transaction. Pull returns rows with change_seq > :cursor for the caller's children, ordered, with a page limit. (Commit-order edge cases are handled by reading only up to the minimum in-flight sequence, or by using a single writer transaction per push.)

9. Authentication Architecture

FlowDesign
RegisterEmail plus password (≥ 12 chars, up to 128; breached-password check via k-anonymity range API; no composition rules). Same 202 response whether the email exists or not.
Email verification256-bit random token, stored hashed (SHA-256), 24 h, single use; login allowed but sync blocked until verified
LoginConstant-time verification; generic error; rate limit 5/min per account and IP with progressive delay; device id recorded
LogoutRevoke the current refresh family; logout-all revokes all families
Forgot / reset passwordSame generic response; token 30 min single use; on reset revoke all sessions and email a notification
Change passwordRequires the current password; revokes other sessions
Account disable / deleteSoft delete with a 14-day grace period, then hard delete of all child data (right to erasure); export endpoint (JSON) before deletion
FutureGoogle / Microsoft sign-in via OIDC (Authorization Code + PKCE), linked to the same verified email
Password hashing: Argon2id (OWASP Password Storage Cheat Sheet first choice). It is memory-hard, so it resists GPU and ASIC cracking better than bcrypt. bcrypt also truncates input at 72 bytes. Baseline parameters: m = 19 MiB, t = 2, p = 1, tuned so one hash takes about 100–300 ms on production hardware. Store the PHC string, which carries the parameters so they can be upgraded on next login. bcrypt (cost ≥ 12) is an acceptable fallback if the platform lacks Argon2.

Session security

ElementDesign
Access tokenJWT, 15 min, claims: sub, sid (family), iat, exp, aud, iss; asymmetric signature with kid rotation; no PII
Refresh tokenOpaque 256-bit random value; server stores only its hash; 30-day sliding window, 90-day absolute limit
RotationEach refresh issues a new token and marks the old one replaced
Reuse detectionPresenting an already-rotated token revokes the entire family (theft signal) and emails the parent
RevocationLogout, password change or reset, account disable; access tokens expire within 15 min (optional deny-list by sid for immediate revocation)
Android storageRefresh token in Keystore-backed flutter_secure_storage; access token in memory; never Hive, logs or crash reports
Web storageRefresh token in an HttpOnly Secure SameSite=Strict cookie; access token in memory. No long-lived tokens in localStorage.

10. Authorization Model

  • Tenant = parent account. Every child, attempt, journey and usage row belongs to exactly one user_id (through child_profiles.user_id).
  • The user_id always comes from the verified token sub and never from the path or body.
  • ChildOwnershipGuard resolves :childId with WHERE id = :childId AND user_id = :sub AND deleted_at IS NULL. If nothing matches it returns 404, not 403, so IDs cannot be enumerated.
  • Sync push validates that every mutation's entity belongs to the caller inside the same transaction. Pull queries join through child_profiles.user_id = :sub.
  • Optional defence in depth: PostgreSQL Row-Level Security with SET app.user_id per transaction.
  • Automated BOLA/IDOR tests: user B's token against every user A resource ID must return 404.
  • Roles for now: parent only. Future: co_parent (invited), teacher (read-only aggregated), modelled as an account_members table.

13. Offline Strategy

  • Offline is the default mode. Every game feature works without a network or an account, exactly as today.
  • The local DB is the source of truth for the UI. The server is the source of truth for cross-device convergence.
  • Online mode only adds background push/pull. Nothing in the gameplay path ever waits on the network.
  • When an access token expires offline, play continues; refresh happens on reconnect. If the refresh fails (revoked), local data is kept and the parent is asked to log in again; pending mutations wait.
  • Logout asks whether to keep local children on the device (default: keep, unlinked) or remove them.
  • Lesson content stays bundled. If a device is on an older contentVersion, server data from newer content is stored but rendered with the device's migration registry. If it is incompatible, the lesson shows "update the app to continue this lesson" while other data stays usable.

14. Conflict Resolution

Scenario: the parent edits the same record on the phone (offline) and on the computer. Principle: no blind last-write-wins for anything that represents learning evidence. Each entity type gets a merge rule that fits its meaning. Optimistic concurrency (version) detects the conflict, and server_updated_at and device_id serve as tie-breakers and audit.

EntityConflict typeResolutionData loss?
unit_attemptsNone possibleAppend-only, immutable, idempotent by id. Both devices' attempts are kept. "Latest" and "best" are computed.No
attempt_objectivesNoneImmutable child rows of an attemptNo
usage_dailyConcurrent incrementsPer-device counter (PK includes device_id); totals = SUM over devices (a G-counter CRDT)No
child_profiles / child_settingsConcurrent editsField-level three-way merge against the base version: disjoint fields are both applied automatically. The same field with different values → for settings (low value) the later server receive time wins and the overwritten value is recorded in audit; for profile identity fields (name, photo, gender) → the server keeps its value, returns a conflict, and the client shows the parent "Phone says X, Web says Y — choose".No silent loss
journeys (in-progress lesson state)Two devices advanced the same lessonProgress-monotonic merge: union of completed step responses, keeping the first recorded outcome per objective (matches the existing AttemptRecorder rule against score inflation); position = the further one (progress_rank); the transient UI state of the losing side is discardedNo assessment loss
Delete vs editOne side deleted a child, the other editedDelete wins (privacy intent, confirmed behind the parent gate). The edit's attempts are quarantined and shown to the parent for 14 days before purge.Recoverable for 14 days
Create duplicatesSame child created on two devices before linkingNever auto-merged by name. The parent sees both and may merge (attempts re-parented, journeys merged by the rule above).No

Per-row metadata on the client: version (last server version seen), sync_status (synced | pending | conflict | quarantined), updated_at (local clock, informational only), last_modified_device. The server keeps version, change_seq and server_updated_at. Device clocks are never used to decide a winner.

18. Migration Strategy (existing local data, zero data loss)

 Existing Hive blob (schemaVersion 3)
   ↓ 1. Local upgrade (offline): parse per child, tolerant; a bad child is isolated, not fatal
   ↓ 2. Write all rows to SQLite in ONE transaction; keep the Hive blob untouched as a backup (≥ 2 releases)
   ↓ 3. Verify counts and checksums (children, attempts, objectives, journeys, usage-days) → else roll back and keep Hive
   ↓ 4. ID normalisation: 'local-child' and non-UUID ids → UUIDv7 (legacy_id kept);
   ↓    attempt ids '{lesson}-{micros}' → UUIDv7 with legacy_attempt_id
   ↓ 5. Parent creates an account or logs in (behind the parent gate)
   ↓ 6. Parent confirms "Link these children to my account" (per child; unlinked children stay local)
   ↓ 7. Initial upload via /sync/push in batches (idempotent mutation ids; resumable after interruption)
   ↓ 8. Server validation: applied → synced; rejected → quarantined locally (shown, never deleted)
   ↓ 9. Pull from cursor 0 (brings children created on other devices)
   ↓ 10. If both sides have children: show both, parent decides merge or keep (no auto-merge)
   ↓ 11. Enable incremental sync

Safeguards: a migration dry-run mode in debug builds; a test matrix of real anonymised blobs from each historic schema (v1, v2, v3 plus each journey version); telemetry-free success flag stored locally; a "rescue export" button in the parent area that writes the raw local data to a user-chosen file.

21. Final Recommendation

B — Refactor the existing application. Keep the Flutter client (Android + Web from one codebase). Rebuild the data layer (typed models, repositories, drift/SQLite, outbox). Add a NestJS + PostgreSQL backend with a REST/OpenAPI contract, parent email authentication (Argon2id, 15-min JWT + rotating refresh tokens with reuse detection, Keystore / HttpOnly cookies) and offline-first sync (push/pull with change_seq cursors, idempotent mutations, optimistic concurrency, per-entity merge rules that never silently lose learning data).

Precondition: revise the "no accounts / no data sending" decision with privacy and legal input before Phase 3.
